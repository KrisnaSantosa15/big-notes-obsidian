## What this PR is

PR 1b fills in the infra/web/spec layer for Aggregate 1 (Answer Dispatch): a student opts in on a new discussion → an AI answer gets requested async. Domain layer (aggregate, VOs, enums, event) already shipped in PR 1a.

Work was tracked as 9 checkpoints, done test-first (TDD). **All 9 are done and committed** (10 commits on this branch, `git log feature/forum-ai-assist/answer-dispatch-domain..HEAD`). PR for this branch is **not opened yet**.

## Done — checkpoints 1–6

1. **Migrations** — `ai_assist_enabled` column on `developer_journey_discussions`; new `forum_ai_assist_answers` table (11 columns — `latency_ms` deliberately dropped, see implementation plan's "Resolved Decision" table).

5. **Shared discussion files** — `NewCourseDiscussion`/`NewDiscussion` carry `ai_assist_enabled` (own commit, cross-domain file convention); `AcademyDiscussionGateway::saveNewCourseDiscussion()` persists it, `getDiscussionById()` now selects it too.

Specification loads the discussion, dispatches the aggregate, persists, calls `AcademyGateway::getCourseLevelAndNameById()` for `course_name`/`levels`, regex-extracts `<img>` URLs from the question HTML for `images[]`, then calls the API gateway. Registered in `GlobalDomainEventServiceProvider::registerForumAiAssistEventHandler()`.

All covered by unit/integration tests (10 unit + 4 integration for the ForumAiAssist-scoped files alone), psalm clean, no regressions in touched shared files (`AcademyDiscussionGatewayTest`, `CreatingNewDiscussionTest`, `SavingNewDiscussionTest`, discussion-comment tests). **Note:** `ForumAiAssistAnswerDispatchSpecification` and `ForumAiAssistAnswerWasRequestedListener` themselves have **no dedicated test** — confirmed this matches house convention for "event → push a queued Specification" (`UpdateCourseVectorEmbeddingSpecification`/`UpdateAIVectorEmbeddingListener` have none either), not a coverage gap.

## Decisions worth knowing before continuing

- **URL naming split (important, easy to get backwards):** every URL **we** expose or call uses `forum-ai` (matches the AI service's own router prefix exactly — `/api/v1/forum-ai/answers`, and our own callback will be `/api/v1/forum-ai/callback`, **not** `-assist`). This was reversed mid-implementation — ADR-0006 originally said `-assist` for the callback, now doesn't. **Internal-only names stay `forum-ai-assist`**: config file (`forum_ai_assist.php`), premium feature key (`forum-ai-assist`), PHP namespace (`ForumAiAssist`). The routes file (`app/routes/forum-ai-assist.php`) doesn't exist yet in this branch — see checkpoint 7 above — but keep the same `forum-ai-assist` filename convention when it's (re-)created.
- **`latency_ms` dropped entirely** — not in the VO, not in the table. "Durasi" (NFR-09) comes from LangFuse trace timing instead. See implementation plan's dropped-columns table.
- **No `$dependsFeature` on the listener's `push()` call.** `Feature::isDisabled($name)` defaults to `true` (disabled) when no `toggles` row exists yet — passing a feature name here without seeding that row silently no-ops every dispatch forever. This was a real bug caught by the checkpoint 6 integration test, not by inspection. If Aggregate 0 (course/discussion indexing, separate branch) uses the same `push()` + `$dependsFeature` pattern, verify it seeded its toggle row before merging.
- **Domain-level guards mirror `ChatbotMessageDispatch`, not just `ai_assist_enabled`.** `ForumAiAssistAnswerDispatch::dispatch()` (PR 1a) also requires the student's account to be verified and enrolled in the course. Integration tests that exercise this need a `course_enrollments` fixture row (`insertNewData('course_enrollments', ['course_id' => …, 'user_id' => …, 'created_at' => …])`) or they'll fail with `NOT_ENROLLED`.
- **Course fixture gotcha:** in this test DB, `course_id = 3` ("Membuat ReactJS AXIOO 2") already has a `course_difficulty_levels` row → `AcademyGateway::getCourseLevelAndNameById(3)->levels` is `['Dasar']`, not `[]`. Don't assume empty levels for that fixture course in new tests.
- **`classroom_v3.0` is globally on, everywhere that matters, except the test DB.** See checkpoint 8 above. Any future Blade/UI work for this feature (slot AI, feedback controls, moderator delete) belongs in the `ui.v3.*` templates, not `ui.newacademies.*` or `ui.v4.*` unless you've independently re-checked the toggle state for that surface.
- **This Blade compiler does not support `@php`/`@endphp`.** Despite running PHP 8.2+, the Blade *compiler* is still Laravel 4.2-era and predates those directives (added in Laravel 5.x). Using them doesn't error — the compiler leaves `@php`/`@endphp` as literal uncompiled text, so any variable assigned inside is `Undefined variable` the moment it's referenced. Use a bare `<?php ... ?>` block instead (see `app/views/ui/v4/academytutorials/widgets/floating/tools.blade.php` for the established pattern). This bit us once this session before being caught.
- **Environment gotcha (costly to rediscover):** `deck`'s PHP container caches opcode/file state — editing a PHP or Blade file and re-running `deck ai:test` immediately can silently run stale bytecode **or a stale source file** with no error, just wrong behavior. This session it took **two `deck restart`s plus manually clearing `DICODING_LOGS/app_storage/views/*`** before an edited Blade file's changes actually took effect. Before concluding a change "isn't taking effect," compare `deck php -r 'echo md5_file("/var/www/dicoding/<path>");'` against `md5sum <path>` on the host — if they differ, `deck restart` first; if the compiled view is still stale after that, delete `DICODING_LOGS/app_storage/views/*` (safe, regenerates automatically) before further debugging. Also, `/tmp` inside the `deck` container is **not** shared with the host — `file_put_contents('/tmp/...')` diagnostics from PHP code are invisible from the host shell. Use `self::fail('DIAG ...')` inside the test itself instead; it reliably surfaces in PHPUnit's failure output.
